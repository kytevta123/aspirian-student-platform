File: ASPIRIAN_MASTER_DEVELOPMENT_ROADMAP.txt Version: 1.0 Status: FINAL
DEVELOPMENT CONTROL DOCUMENT Project: Aspirian Student Platform Website:
aspirian.pk Application: app.aspirian.pk

PURPOSE

This document is the permanent master roadmap for the actual development
of the Aspirian Student Platform.

It is intended to remain as a standalone record outside the ChatGPT
conversation. It defines the development order, workflow, task execution
method, Git workflow, Copilot workflow, testing rules, deployment
process, and project completion path.

The existing project documentation remains the primary source of truth
for architecture and module specifications. This document controls HOW
development is executed.

IMPORTANT PROJECT RULE

Do not rebuild or redesign the complete architecture during
implementation.

The approved documentation must be treated as the baseline.

Changes are allowed only when a genuine technical, security,
scalability, business, or implementation requirement is identified and
the impact is reviewed and documented.

========================================================= 6. GITHUB
COPILOT STRATEGY
=========================================================

Copilot is a coding assistant.

Copilot is NOT the project architect.

The architecture, module boundaries, security rules, and development
order come from the approved project documentation.

Copilot should be used for:

-   Code generation
-   Code completion
-   Refactoring
-   Test generation
-   Error investigation
-   Debugging assistance
-   Documentation assistance
-   Small implementation tasks

Copilot should NOT independently:

-   Redesign the entire system
-   Change architecture without approval
-   Delete unrelated files
-   Rewrite large sections unnecessarily
-   Introduce random packages
-   Change database structure without checking documentation
-   Change API contracts without review
-   Expose secrets
-   Commit credentials or API keys

========================================================= 7. COPILOT
TASK WORKFLOW =========================================================

For every significant task:

STEP 1 Select one task from TASKS.md.

STEP 2 Read the relevant documentation.

STEP 3 Ask Copilot to inspect the existing implementation.

STEP 4 Ask Copilot for an implementation plan BEFORE coding when the
task is non-trivial.

STEP 5 Review the proposed plan.

STEP 6 Approve implementation.

STEP 7 Implement only the selected task.

STEP 8 Run relevant tests.

STEP 9 Fix problems.

STEP 10 Run tests again.

STEP 11 Review changed files.

STEP 12 Commit to Git.

STEP 13 Push to GitHub.

STEP 14 Update CHANGELOG.md when the change is significant.

STEP 15 Move to the next task.

========================================================= 8. STANDARD
COPILOT CONTEXT PROMPT
=========================================================

Use a prompt similar to this for major tasks:

“We are developing the Aspirian Student Platform.

Use the existing project documentation as the source of truth.

Relevant documentation: - ARCHITECTURE.md - PROJECT_SPEC.md -
DATABASE.md - DEVELOPMENT_ROADMAP.md - MILESTONES.md - SPRINT_PLAN.md -
TASKS.md

Current task: [TASK ID] — [TASK NAME]

Before coding: 1. Inspect the current project structure. 2. Check
relevant existing implementations. 3. Identify dependencies. 4. Do not

required database/API/security changes. 7. Provide an implementation
plan.

Wait for approval before implementing a non-trivial task.”

========================================================= 9. STANDARD
IMPLEMENTATION PROMPT
=========================================================

After the plan is reviewed:

“Proceed with the approved implementation for [TASK ID].

Rules: - Follow the existing architecture. - Modify only required
files. - Do not introduce unnecessary dependencies. - Follow existing
coding conventions. - Protect existing functionality. - Add or update
tests where required. - Do not change unrelated modules.

After implementation: 1. List changed files. 2. Explain important
changes. 3. Run relevant tests. 4. Report test results. 5. Report any
remaining issues. 6. Do not start the next task automatically.”

========================================================= 11. TASK
EXECUTION RULE =========================================================

One task should be considered complete only when it is VERIFIED.

TASK LIFECYCLE:

TODO | v IN PROGRESS | v TESTING | v REVIEW | v DONE

If a task cannot proceed:

BLOCKED

A blocked task must record the reason.

========================================================= 12. DEFINITION
OF DONE =========================================================

A task is DONE when:

-   Implementation is complete
-   Relevant validation is complete
-   Relevant tests pass
-   Security has been considered
-   No critical error remains
-   Changed files are reviewed
-   Documentation is updated where required
-   Git commit is created
-   GitHub push is completed

A feature is DONE only when its required tasks are DONE.

========================================================= 14. GIT COMMIT
RULES =========================================================

Commits should be:

-   Meaningful
-   Focused
-   Related to a task
-   Easy to understand
-   Free from secrets

Examples:

“Implement user registration” “Implement user login” “Add question
duplicate detection” “Implement test submission” “Add student dashboard”
“Add mobile API authentication”

Avoid vague commits such as:

“changes” “update” “fix stuff” “final”

========================================================= 15. GIT SAFETY
=========================================================

NEVER commit:

-   Passwords
-   API keys
-   Database credentials
-   Private tokens
-   Production secrets
-   .env files containing secrets
-   Private certificates unless specifically required and protected

Use environment variables and secret management.

Before every push, check:

-   Git status
-   Changed files
-   Sensitive files
-   Diff where appropriate

========================================================= 16. DATABASE
DEVELOPMENT RULES
=========================================================

Database changes must be controlled.

Before a major database change:

1.  Review DATABASE.md.
2.  Review relationships.
3.  Check existing migrations.
4.  Create proper migration.
5.  Test migration.
6.  Verify constraints.
7.  Verify indexes.
8.  Test rollback strategy where applicable.
9.  Run application tests.

Never casually edit production database structures manually.

========================================================= 17. API
DEVELOPMENT RULES
=========================================================

Before changing an API:

-   Check existing API contract
-   Check web clients
-   Check mobile clients
-   Check authentication
-   Check authorization
-   Check validation
-   Check response format
-   Check versioning requirements
-   Update API documentation
-   Run regression tests

Breaking API changes must be explicitly documented.

-   Authorization
-   Password hashing
-   Session/token security
-   Input validation
-   Output validation
-   CSRF protection
-   XSS protection
-   SQL injection prevention
-   Rate limiting
-   File upload validation
-   Access control
-   Secure headers
-   Secret management
-   Audit logging where required

Security issues receive high priority.

========================================================= 20. ERROR
HANDLING WORKFLOW
=========================================================

When an error occurs:

1.  Capture exact error.
2.  Identify affected task.
3.  Reproduce error.
4.  Inspect logs.
5.  Determine root cause.
6.  Fix only the required area.
7.  Run relevant tests.
8.  Run regression tests if necessary.
9.  Verify again.
10. Commit the fix.

Do not repeatedly ask Copilot to “try random fixes.”

========================================================= 41. WHEN
COPILOT PRODUCES BAD CODE
=========================================================

If Copilot creates incorrect code:

1.  Do not blindly accept it.
2.  Review the code.
3.  Compare it with documentation.
4.  Run tests.
5.  Identify the exact issue.
6.  Give Copilot the specific error/context.
7.  Fix the smallest required area.
8.  Test again.

If Copilot repeatedly proposes an incorrect architecture, stop and
review the task before continuing.

========================================================= 42.
DEVELOPMENT SESSION ROUTINE
=========================================================

At the beginning of a development session:

1.  Check Git status.
2.  Pull latest changes where appropriate.
3.  Identify current task.
4.  Read relevant documentation.
5.  Confirm dependencies.
6.  Plan implementation.

During development:

1.  Make focused changes.
2.  Test frequently.
3.  Review diffs.
4.  Avoid unrelated modifications.

At the end:

1.  Run tests.
2.  Review Git diff.
3.  Commit.
4.  Push.
5.  Record important changes.
6.  Note the next task.
