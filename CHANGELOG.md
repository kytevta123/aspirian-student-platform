---

# 3. Versioning Strategy

The project follows semantic versioning:

```
MAJOR.MINOR.PATCH
```

Example:

```
1.0.0
```

Where:

```
MAJOR
Breaking architectural or API changes

MINOR
New features without breaking existing functionality

PATCH
Bug fixes and small improvements
```

# 29. Change Management Rule

Future changes must not be made randomly.

Every significant change should:

1. Be identified
2. Be evaluated
3. Check dependencies
4. Check architectural impact
5. Be documented
6. Be implemented
7. Be tested
8. Be added to this CHANGELOG

---

# 30. Architecture Protection Rule

The approved project architecture should remain stable during development.

Changes should only be introduced when they provide a clear technical or business benefit.

Avoid unnecessary restructuring after implementation has started.

---

# 31. Breaking Changes

Any breaking change must clearly document:

* What changed
* Why it changed
* Which modules are affected
* Which APIs are affected
* Migration requirements
* Backward compatibility considerations

---
